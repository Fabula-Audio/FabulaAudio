# Причина проблемы сохранения и исправление

## Что было опасно
В предыдущей версии уже была устранена основная ошибка 4.10, где `saveResult()` повторно вызывал `ensureStage(currentStage)` и тем самым создавал второй путь выбора исходного файла для сохранения.

В 4.12 fixed22 сделано жёстче:

1. Готовый файл хранится в одном поле:
   `currentResultFile: File?`.
2. Единственное положительное присваивание:
   `currentResultFile = file`
   находится в `publishCurrentResult()` и вызывается после успешного построения выбранного этапа.
3. `Прослушать результат` читает только `currentResultFile`.
4. `Сохранить результат` читает только `currentResultFile`.
5. `saveResult()` больше не строит/не ищет этап повторно.
6. Для имени файла используется режим, относящийся к этому готовому результату: `currentResultStage`.
7. В коде отсутствуют типичные опасные конструкции `stageFiles[0]`, `fabula_speed_0` и повторный `ensureStage(currentStage)` внутри сохранения.

## Почему `currentResultStage` не является вторым источником файла
`currentResultStage` хранит только метаданные готового `currentResultFile` — какой суффикс нужен для уже выбранного файла. Сам путь/объект `File` никогда из этого значения не вычисляется.

## Итог
При сохранении используется тот же объект `File`, который используется кнопкой «Прослушать результат». Это устраняет расхождение между тем, что пользователь слышит, и тем, что передаётся в `FABULA_SAVE`.
